# Palettium ET4000AX backend (updated v0037)

This is an **incremental patch** to the user's v0.5 tree. It does not replace
`rgfx.h`, `rgfx.c`, `rg_hardware.h`, or any of the four Windows targets.

## Design

* Hardware-independent `RG_Device` + software drawing remain unchanged.
* Native Tseng backend implements read/write bank selection at port `3CDh`.
* Backends receive a platform port/aperture service table (`ET4K_Port`).
* DOS, Win16 and Win9x wrappers can supply different platform services.
* No use of VESA; the DOS smoke test asks the card BIOS to enter its native
  `2Eh` or `2Fh` graphics mode according to verified VRAM. Full
  register-level native mode setting is future work.
* Hardware acceleration overrides remain optional; ET4000AX installs none.
* Packed 640x400x8 (Tseng BIOS 2Fh, 256000 bytes) fits 256 KiB cards;
  packed 640x480x8 (2Eh, 307200 bytes) requires at least 512 KiB.
  The backend accepts verified 256 KiB, 512 KiB, or 1 MiB VRAM sizes.
  A BIOS or read-only platform query can veto modes; successful mode setting
  is still required. Planar 640x480x16 is a separate, unfinished renderer.

## Build 16-bit DOS smoke test

With Open Watcom v2 on PATH and WATCOM configured:

```sh
sh dos/build-et4k.sh
```

This produces `build/dos/ET4KTEST.EXE` if the 16-bit DOS toolchain is
configured correctly. The maintainer built and ran this DOS executable on November 23, 2026 in
86Box at **256, 512 and 1024 KiB**; graphics appeared correct at all three
VRAM capacities. The portable host regression tests also pass.
Copy the executable into a disposable VM using a floppy image. In 86Box
select an ET4000AX with **known** 256/512/1024 KiB VRAM and boot DOS (not
Windows). Run `ET4KTEST 256`, `ET4KTEST 512`, or `ET4KTEST 1024` to match
that exact 86Box setting. The program will not assume 1 MiB VRAM and will
not auto-detect size destructively. On 256 KiB it requests 640x400x256;
otherwise 640x480x256. Run only in a recoverable VM. You should see a colored gradient with crossed
lines. Press a key to restore 80x25 text mode. A readback PASS message appears
on success. If the display is wrong, do not assume a PASS establishes video
mode correctness: the BIOS mode needs separate verification.

## Constraints and next steps

* The platform is responsible for native graphics-mode selection, hardware
  register initialization and framebuffer aperture mapping.
* `et4k_setup` needs an accurately configured VRAM capacity. The DOS sample
  requires an explicit size to avoid overrunning smaller cards. The backend
  guards banked offsets beyond the supplied capacity; supplying a falsely
  larger capacity defeats this protection. An optional read-only capacity
  query can be supplied by an OS adapter in future.
* No chipset identification is yet performed. It is intentionally dangerous
  to run this DOS experiment against a non-Tseng adapter.
* Bank switching must be set up for graphics mode by the mode provider.
* Future Win16 driver must implement full GDI semantics and its separate
  platform port/memory services; this is not an installable `.DRV`.
* For a later W32 backend, reuse this framebuffer implementation only after
  testing chipset-specific differences.

## Win16 hardware adapter (v0030)

The new `windows/win31/pal_et4k_win16.c` supplies hardware callbacks for
ET4000AX banking (`inp`/`outp`, port 3CDh), memory aperture byte access
(via Windows KERNEL `__A000H` exported protected-mode selector), and
BIOS INT 10h mode changes with AH=0Fh mode readback and restore. Never
assume that the DOS real-mode `A000:0000` segment works in protected mode.
Neither the native adapter nor `pal_et4k_session.c` is called from Win3.1
DDI Enable yet. This adapter does **not** attempt to detect installed VRAM
or mark the driver installable. The size still must be verified externally.
Standard-mode DOS switching and 386-enhanced VDD integration remain to be
implemented; raw BIOS-mode programming is not sufficient for all lifecycle
transitions. Avoid experimenting outside a recoverable VM.

## v0036: ROM and CRTC memory-configuration diagnostic (NOT detection)

User-supplied 86Box BIOS images were audited at v0036. V8 and earlier V1
series BIOSes differ in admission tests for ET4000 extended modes. The
**configured** memory bus and memory-chip depth are described by CRTC
register `37h`, but the register alone does not prove fitted/working VRAM.
A BIOS may protect this register, and the chip may not be ET4000.

`et4k_crtc37_snapshot` is **diagnostic only**. It reads VGA Misc Output
`3CCh` to choose the color CRTC `3D4h/3D5h` or mono `3B4h/3B5h`; it reads
and saves the current CRTC index, **writes that index port to select 37h**,
reads the CRTC data port, then restores the original index. It never writes
CRTC DATA, `3CDh`, VRAM, or a mode register. The only port writes are the
two CRTC **index** selects. This is not appropriate to invoke directly from
386 Enhanced Windows without a proper VDD contract.

`et4k_crtc37_decode` reports the documented bus-width/depth product as a
**candidate capacity** (8/16/32-bit bus × nominal 64K/256K chip depth),
including candidates smaller than 256 KiB that Palettium doesn't support.
Do **not** pass this value to `et4k_setup` as verified capacity. The CRTC
value can be stale, locked, BIOS-dependent, or incompatible with a board.

Under plain DOS with an ET4000AX installed, after rebuilding with Open Watcom:

```sh
sh dos/build-et4k.sh
```

Run `ET4KTEST INFO` in the DOS VM for a *no-mode-switch* reading of the
C000h option-ROM version/date hint and CRTC `37h`. Then compare results at
256/512/1024 KiB, ideally with the V8.01X, V8.06X and V1.x BIOS variants.
For existing graphic tests, `ET4KTEST 256|512|1024` prints the same
information and then runs the previously validated drawing test. In every
case use a disposable/recoverable 86Box VM with an ET4000AX installed and
**boot plain DOS, not a DOS window inside Windows**. `INFO` still performs
raw I/O-port reads and two index-port writes; it does not touch VRAM.

ROM-identification hints read the *C000h* standard 32-KiB option-ROM header
and the version/date offsets observed in the six uploaded ROM images. They
are not a general-purpose BIOS fingerprint or authentication check. A ROM
loaded elsewhere or an unfamiliar ROM will be reported as unrecognized.

The v0035 86Box Windows 3.1 screenshot showed the *configured* VDD was
`*vddvga`. That is a separate driver-installability problem; CRTC37 hints
and BIOS disassembly do not establish VDD compatibility or make the dormant
Win16 native ET4000 adapter safe to activate.

## v0037: capacity hint vs Windows startup permission

The maintainer tested `ET4KTEST INFO` in plain 86Box DOS against the
three option BIOS families V8.01X, V8.06X, and V1.21X, each configured
with 256/512/1024 KiB: **9/9 correct hints** (`0Dh`/`0Eh`/`0Fh`).
No physical-card VRAM detection was established. A port snapshot is
**not** safe simply because the same read succeeded under DOS.

The Win3.x startup planner therefore needs an explicit VRAM setting.
CRTC37 may only reject contradictions, never silently supply authority.
During Win16 `Enable(style=1)`, the adapter reads the explicit
`SYSTEM.INI [Palettium] VRAMKiB` value and the configured VDD entry.
This does not touch hardware and is not part of the card-neutral backend.
The planner's `can_enable` flag remains zero. With enhanced-mode `*vddvga`,
a 640x480x8 framebuffer is excluded; even 640x400x8 has **unverified**
VDD compatibility. Device installation remains blocked.

Correct 16-bit DOS executable: **`build/dos/ET4KTEST.EXE`**. The
similarly named **`tests/exes/et4k-test`** is a Linux ELF host regression.
Copying/renaming the latter into a DOS VM previously caused a reboot.
