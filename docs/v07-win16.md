# Palettium v0.7: Win16 core cross-compile gate

## Why this gate exists

Our ET4000AX DOS experiment passed in 86Box. The next *independent* risk is
whether our common C89 rasterizer and ET4000 framebuffer sources are suitable
for the Win16 compiler/data model, especially 16-bit `int` and far pointers.

This incremental patch builds the **same** `common/rgfx.c`,
`common/rg_hardware.c`, and `hardware/tseng/et4000ax/et4k.c` into a Win16
DLL. It does not alter these existing sources or introduce Windows types into
them. `PALCORE.DLL` is **not** a GDI driver, and must **not** be installed
as a display driver.

## Build

```sh
cd ~/dev/palettium
sh windows/win31/build-palcore.sh
file windows/win31/PALCORE.DLL
```

`PalettiumCoreSelfTest()` initializes a small callback framebuffer, then
exercises the real common library's pixel, horizontal line, rectangle fill
and overlapping-capable blit interface. Return 0 means success; bitwise
nonzero means failures. This routine is **compiled but not executed** just
by building the DLL. We must add a Win16 calling test program later.

Expected compiler model: `-mc -bd -zu -bt=windows -l=windows_dll`.
The portable code should *not* assume C pointers can reach an entire 640x480
framebuffer; the Windows adapter will map and bank A000h through a platform
service implementation.

### Report back

Please send the full output of `sh windows/win31/build-palcore.sh`, even if
it fails. This environment has a C89 Linux compiler but no Open Watcom.
Don't treat a successful link as proof that a Windows GDI display driver
can run.

## Verified GDI work ahead

Windows 3.1 driver implementation is not an ordinary Win16 DLL. We will
build a GDI adapter against actual DDK structures, with precise exports,
`Enable`'s two-phase protocol, screen PDEVICE/GDIINFO, color/brush/pen
semantics, cursor and text handling, and eventual VDD coordination. The
Video 7 256-color driver from the 3.1 DDK provides a useful ABI reference.

In 386 Enhanced Mode, DOS-session video switching involves a Virtual Display
Driver (VDD) and separate grabber behavior. This is distinct from the
ET4000 banked-framebuffer module and must not leak into it. It is reasonable
to aim for initial Standard Mode bring-up before adding enhanced-mode DOS
window support.

Long-term targets: Windows 3.1, WfW 3.11, Windows 95 and Windows 98, built
from the same hardware backend with separate OS-level GDI/VDD components.
